# Model API, OpenRouter with your own key

Source: nanoMuse docs/own-key.md and nanomuse/llm/providers.json, checked in 2026-10. The canonical provider catalogue is nanomuse/llm/providers.json. The JSON file in this PR is an excerpt for review. Do not treat the excerpt as the canonical catalogue. The canonical file is generated by scripts/providers-json.mjs in the upstream tree.

## Decision

Use the nanoMuse own-key model. Do not hard code one model. Use the provider catalogue plus four jobs: Chat, Operating the screen, Making pictures, Making clips.

OpenRouter: protocol openai, base URL https://openrouter.ai/api/v1, key shape sk-or-v1-..., capabilities chat, vision, image.

Defaults from the catalogue, OpenRouter entry:

- chat: deepseek/deepseek-v4.1-flash
- hands: qwen/qwen3.8-27b, needs image reading capability
- image: openai/gpt-image-2, through the OpenRouter Image API at /api/v1/images
- video: none. OpenRouter has no video in this catalogue. Clips are Bailian only in this catalogue.

A provider without a capability does not offer that function. The UI states which provider is missing, in one sentence. It does not fail silently.

## Four jobs, Settings, Models

| Row | Use | OpenRouter covers it |
|---|---|---|
| Chat | Conversation | Yes |
| Operating the screen | Look at screenshots and operate the phone | Yes, with a vision model |
| Making pictures | Avatar and pictures | Yes, with an image output model, through the Image API |
| Making clips | Avatar short videos | No |

## Key handling

Keys go through the Secure Vault or Android Keystore. They are not pasted in chat, not written to logs, not committed to the repository, and not written in plain text in config.toml.

After the first save, a card asks what this key handles: one switch per job the provider can do (chat, operating the screen, making pictures, making clips), all on. Use it moves those rows to this provider, on the catalogue default model for each job, or the first model in its list that fits. Not now changes nothing, and so does a switch that is off.

After turning off nanoMuse Cloud, when the chat model is still the Cloud model and there is no own chat model, the app refuses and asks the user to add a provider of their own first, in its own words, following the same rule as nanoMuse.

When a model of your own fails, nothing falls back on its own. The error card offers Use nanoMuse Cloud this time, for that one turn only, and changes no row.

## Local execution and network inference

Local execution on the phone and whether model inference uses the network are two separate choices.

Using a network model means task text and screenshots that may contain personal information go to the selected model provider, here OpenRouter. The architecture keeps the model pluggable, so a local model can replace it later. A cloud runtime is not a required component.

Network note for mainland China: OpenRouter is marked global in the catalogue. It bills pay as you go and needs an international card. Bailian is the first pick for mainland China in the catalogue, with one key for all four jobs. The user chose OpenRouter. This note follows OpenRouter and lists Bailian only as an alternative. It does not change the choice.

## Config example, runtime config.toml style, no real key

```toml
[llm]
provider = "openrouter"
# api_key is not written here. It comes from Secure Vault or Android Keystore.
# base_url and default models come from the provider catalogue. Do not hard code them.
# chat = "deepseek/deepseek-v4.1-flash"
# hands = "qwen/qwen3.8-27b"

[image]
provider = "openrouter"
# image = "openai/gpt-image-2"
```

## Acceptance

- The OpenRouter key saves through a secure card, not through chat.
- Settings, Models shows four rows, each as provider, model, and lists only models that can do that job.
- With no video capability, the Making clips row states the missing capability. It does not crash.
- One Chat round succeeds and returns provider, model, and usage. On failure, the error card offers the one time Cloud option. It does not switch automatically.
